你现在的 SF100 结果证明的是：

BaseGraph + Delta 路径能跑 SF100，而且内存不是瓶颈。

但 SemL0 论文真正要证明的是：

query-semantic physical design 能减少 LSM L0 read amplification。

这两件事相关，但不是同一件事。

这比继续跑更大数据更重要。因为审稿人最关心的是：

你的 semantic design 到底比 graph-aware L0、degree-aware、schema-only 强在哪里？

你现在架构文档里已经有 graph-aware L0、RA-score targeted compaction、SourceBloom、CSR Metadata Cache 等机制。 这很好，但也意味着你必须把 baseline 拆清楚。否则审稿人会说：

所以第一优先级不是优化 IC14，而是补 ablation / baseline。

第二优先级：补写入与维护代价

SemL0 的核心代价是：

semantic metadata 变多；
L0 segment 可能更碎；
manifest 可能变大；
flush / compaction 更复杂；
feedback compaction 会产生 rewrite cost。

如果你只给 read bytes reduction，顶会审稿人一定会问：

你是不是用更多文件、更大 metadata、更高写放大换来了读性能？

第四优先级：补一个真正强的 baseline

你现在最缺的不是“更大规模”，而是“外部对照”。

至少要有：

schema-only LSM-CSR baseline
当前 graph-aware L0 baseline：src_label + edge_type
SemL0 budgeted semantic
full semantic upper bound
no-feedback vs feedback compaction

如果时间允许，再加：

LSMGraph-style baseline
RocksDB/KV-style encoding baseline
LiveGraph / Teseo / GraphOne 中至少一个可复现实验或定性对比

对你来说，最现实的是先做内部可控 baseline。因为你的架构已经支持 graph-aware L0 分区、RA-score targeted compaction、SourceBloom 和 metadata cache。 你可以通过开关把它们拆开做 ablation。
